# Operational Guide For The Generated Harness

This guide describes how to use the harness inside a project generated by the
template.

## Project Status

Main command:

```bash
python3 scripts/project_status.py
```

Shows the feature queue, active feature, active runs and the last completed run.

Useful files:

- `state/project.json`: versioned project configuration.
- `state/workflow.json`: transitions and roles.
- `data/<project_id>/control/queue.json`: operational queue.
- `data/<project_id>/control/runtime.json`: operational runtime.

## Register A Feature

```bash
python3 scripts/register_feature.py \
  --title "Add export command" \
  --slug add-export-command \
  --description "Permite exportar el estado del proyecto a JSON." \
  --priority 10 \
  --requested-by "operator" \
  --change-domain product
```

Domains:

- `product`: product changes.
- `harness`: controlled harness maintenance.
- `template`: template changes.

Per-feature capability:

```bash
python3 scripts/register_feature.py \
  --title "Harden parser" \
  --slug harden-parser \
  --description "Endurece el parser y requiere mutation testing." \
  --capability mutation-testing
```

## Prepare Specification And Architecture

The specifier completes the documents under:

```text
specs/features/<feature-slug>/
  specification.md
  acceptance.yaml
  architecture.md
  implementation-plan.md
  test-plan.md
```

Transitions:

```bash
python3 scripts/transition_feature.py \
  --feature F-001 \
  --to SPEC_READY \
  --role specifier \
  --reason "Spec v2 completa y acceptance verificable."

python3 scripts/transition_feature.py \
  --feature F-001 \
  --to DESIGN_READY \
  --role architect \
  --reason "Architecture incluye Specification Review sin bloqueos."

python3 scripts/transition_feature.py \
  --feature F-001 \
  --to READY_FOR_DEVELOPMENT \
  --role leader \
  --reason "Scope aprobado para implementacion."
```

## Implementation

The implementer requests a lease and worktree:

```bash
python3 scripts/start_implementation.py --feature F-001 --agent-id implementer-1
```

The script records the run and creates an isolated worktree. The implementation
is done in that worktree.

Two safeguards at startup:

- If the feature's branch or worktree already existed (resumption), they are
  resynchronized with the canonical branch via `git merge --no-edit` before
  creating the lease (`[INFO] Resync` in the output). A conflict or a dirty
  worktree aborts with exit 2 without writing anything to the control plane.
- If any other implementer lease exists (even if its feature is `BLOCKED` or the
  lease has expired), startup is rejected with an error that points to
  `scripts/recover_stale_leases.py`. This preserves the Role Guard invariant of
  a single active implementer lease.

When finished:

```bash
python3 scripts/complete_implementation.py \
  --feature F-001 \
  --agent-id implementer-1 \
  --reason "Implementacion lista con gates fast verdes."
```

This phase runs the `implementation_fast` quality gates. A failed blocking gate
prevents moving to `READY_FOR_QA`.

## QA

Start:

```bash
python3 scripts/start_review.py --feature F-001 --agent-id qa-1
```

Complete with approval:

```bash
python3 scripts/complete_review.py \
  --feature F-001 \
  --agent-id qa-1 \
  --verdict APPROVED \
  --summary "QA aprobado con suite completa y evidencias validas."
```

Complete with changes requested:

```bash
python3 scripts/complete_review.py \
  --feature F-001 \
  --agent-id qa-1 \
  --verdict CHANGES_REQUESTED \
  --summary "QA encontro una regresion verificable." \
  --required-change "Corregir el caso limite documentado en el test plan."
```

QA runs the `qa_full` gates. `APPROVED` is not allowed if the blocking gates
fail.

## Finalization

```bash
python3 scripts/finalize_feature.py \
  --feature F-001 \
  --reason "Feature aprobada e integrada."
```

Finalization runs the `finalization` gates, integrates the approved feature and
moves the state to `DONE`.

If `acceptance.yaml` declares documentation requirements under `documentation`,
finalization validates that the QA-reviewed changes include the required
updates. Examples:

- `requires_adr: true` requires a change in `docs/10-architecture/adr/`.
- `requires_runtime_update: true` requires a change in `docs/20-runtime/`.
- `requires_operations_update: true` requires a change in `docs/40-operations/`.
- `requires_quality_update: true` requires a change in `docs/30-quality/`.

## Git Publication

If the project has `git_publication.enabled: true`, a finalized feature can be
published with:

```bash
uv run python scripts/publish_feature.py --feature F-001
```

The recommended agent is `repository-publisher`. The agent must not run
`git push` directly; the Role Guard blocks it.

Supported modes:

- `local`: records evidence of local integration.
- `dry_run`: verifies that the remote push would be possible.
- `push`: pushes the canonical branch to the configured remote.
- `disabled`: disables publication.

The evidence is left in:

```text
artifact_root/git-publish/<feature>/
```

To enable remote push in a generated project, configure `state/project.json` or
`project.yaml`:

```yaml
capabilities: [git-publish]
git_publish_mode: push
git_publish_remote: origin
git_publish_branch: main
```

## Mutation Testing

For features with the `mutation-testing` capability:

```bash
python3 scripts/mutation_runner.py \
  --feature F-001 \
  --output "$ARTIFACT_ROOT/mutation-tests/F-001/latest.json" \
  --max-mutants 100 \
  --max-duration-seconds 600 \
  --test-command python3 -m pytest -q
```

The mutation reviewer must record evidence in:

```text
evidence/mutation-reviews/F-001.json
```

Approval requires zero relevant surviving mutants without justification. Any
`test_gap` must produce `CHANGES_REQUESTED`.

## Project Documentation

Generated projects have a stable technical structure under `docs/`:

- `docs/00-project/`
- `docs/10-architecture/`
- `docs/20-runtime/`
- `docs/30-quality/`
- `docs/40-operations/`
- `docs/50-releases/`
- `docs/90-generated/`

The concrete feature specs live in `specs/features/`. The regenerable summaries
live in `docs/90-generated/` and are not a source of truth.

To refresh the derived documents:

```bash
python3 scripts/refresh_project_docs.py
```

Individual scripts:

```bash
python3 scripts/generate_docs_index.py
python3 scripts/refresh_feature_index.py
python3 scripts/refresh_quality_summary.py
python3 scripts/refresh_metrics_summary.py
```

## Recovery

If a lease gets stuck (for example, `start_implementation.py` rejects startup
due to another implementer's lease):

```bash
python3 scripts/recover_stale_leases.py --all
```

The script only recovers expired leases (`expires_at` past): it deletes the
lease, marks the run as `EXPIRED` and leaves the feature in `BLOCKED` if it was
in progress. To release a non-expired lease, wait for its expiration or expire
it explicitly as the operator.

If you need to inspect locks, leases or runs, check
`data/<project_id>/control/`, but apply state changes only through scripts.

## Common Problems

### `uv` Does Not Appear In Non-Interactive SSH

The verification scripts export `PATH="$HOME/.local/bin:$PATH"` and fall back to
`.venv/bin`. If it still fails, check:

```bash
which uv
ls -la "$HOME/.local/bin/uv"
```

### A Blocking Gate Fails

Look for the JSON evidence in:

```text
artifact_root/quality-gates/<feature>/
```

The small JSON points to the heavy log with stdout/stderr.

### QA Cannot Approve

Check:

- the feature's current state
- the active QA lease
- that the worktree has not changed since `reviewed_commit`
- the `qa_full` gates
- mutation evidence if the feature requires `mutation-testing`

### Git Publish Fails

Check:

- the feature is in `DONE`
- the canonical repository is clean
- the current branch is the canonical one
- `merged_commit` matches `HEAD` if `require_merged_head` is active
- the configured remote exists for `dry_run` or `push`
- the host's Git credentials allow writing to the remote
